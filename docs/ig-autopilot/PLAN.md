> 매일 아침 RSS로 이슈 수집 → 중복 표시 → 분류 → 2026 알고리즘에 맞춘 캐러셀 초안 생성
> 작성일: 2026-08-03

**확정 사항** — 니치: 창업·부업·수익화 / 범위: 자동 게시(Phase 5)까지 / 계정: 프로페셔널 + FB 페이지 연결 완료

## 0. 한 줄 요약

**결정론적인 일(수집·중복판정·렌더링)은 Node 스크립트가**, **판단이 필요한 일(어떤 이슈를 콘텐츠로 만들지, 카피)은 Claude Code가** 맡는 하이브리드 파이프라인. 게시는 Meta 공식 Graph API만 사용하고, 마지막 발행 버튼은 항상 사람이 누른다.

## 1. 리서치 결과 — 2026 인스타그램 알고리즘

### 1-1. 무엇이 바뀌었나

| 신호 | 2024까지 | 2026 현재 |
|---|---|---|
| **DM 공유 (sends per reach)** | 보조 지표 | **최상위 신호.** DM 공유 1회 ≈ 좋아요 15회 수준의 배포 가중치 |
| **저장 (saves)** | 보조 지표 | 좋아요보다 3~5배 강한 신호. "다시 볼 가치" 판정 |
| **시청 시간 / 체류** | 릴스만 | 전 표면(피드·릴스·탐색) 공통 최상위 신호 |
| **프로필 클릭** | 미반영 | 배포 재조정 신호로 편입 |
| **좋아요 · 팔로워 수** | 핵심 | **가중치 급락.** 팔로워 수는 배포에 거의 영향 없음 |

핵심 문장 하나로 줄이면 — **"좋아요를 받는 콘텐츠"가 아니라 "남에게 보내고 싶고, 저장해두고 싶은 콘텐츠"가 퍼진다.**

### 1-2. 주력 포맷은 '정보성 릴스'

캐러셀과 릴스는 잘하는 일이 다르다. **목표가 도달이면 릴스가 맞다.**

| | 릴스 | 캐러셀 |
|---|---|---|
| 역할 | **발견 엔진** — 조회 대부분이 **비팔로워**에서 나온다 | 전환 엔진 — 기존 팔로워의 신뢰를 깊게 한다 |
| 도달 | 캐러셀보다 **36% 높음** | 참여율은 높으나(10.15% vs 6%) 주로 팔로워 대상 |
| 쓸 때 | 새 사람에게 닿고 싶을 때 | 이미 팔로우한 사람의 저장·재방문을 얻을 때 |

계정을 키우는 단계에서는 릴스가 정답이다. 비팔로워 배포를 결정할 때 인스타가 보는 건 **DM 공유**이고, 정보성 릴스는 저장 점수도 특히 높다.

**대신 릴스는 첫 3초가 전부다.**
- 시청자 최대 **50%가 첫 3초 안에 이탈**한다
- **3초 유지율 60% 이상인 릴스는 40% 미만 대비 도달이 5~10배**
- 스킵률이 낮아야 더 넓게 배포된다

그래서 1번 화면의 후킹, 화면의 지속적인 움직임, 큰 자막이 전부 알고리즘 문제로 직결된다.

캐러셀도 렌더러를 남겨뒀다(`render.mjs`). 팔로워가 쌓인 뒤 저장·재방문용으로 병행하면 된다.

### 1-3. 콘텐츠 제작 규칙 (템플릿에 그대로 코드화할 것)

| 항목 | 규칙 |
|---|---|
| 길이 | **20~40초 권장.** Graph API는 5~90초 + 9:16이어야 릴스 탭에 노출한다. 벗어나면 일반 동영상으로 게시됨 |
| 슬라이드 수 | **7~9장**. 장당 3초 안팎이면 자연히 이 길이가 나온다 |
| 슬라이드당 메시지 | **1슬라이드 = 1메시지**, 30~50자 |
| 1번 슬라이드 | 손실 회피형("이거 모르면 손해") 또는 숫자 약속형("~하는 7가지"). 인사말·브랜드 자랑 금지 |
| 첫 3초 | **여기서 절반이 이탈한다.** 후킹 문장이 0.5초 안에 다 보여야 한다 |
| 움직임 | 정지 화면은 즉시 스크롤당한다. 전 구간 켄번스 팬을 건다 |
| 전환 | **slideup** (겹치지 않는 전환). 크로스페이드는 두 텍스트가 겹쳐 읽히지 않는 구간을 만든다 |
| 자막 | 크게, 강조어는 컬러로. 소리 없이 봐도 완결되어야 한다 |
| 마지막 -1장 | **요약 카드** — 저장 유발의 핵심 지점. 다른 장보다 길게(4.5초) 둬서 스크린샷할 틈을 준다 |
| 마지막 장 | CTA — "저장해두세요" + **"이거 알아야 할 사람에게 보내세요"** (DM 공유 유도 = 최상위 신호 직접 겨냥) |
| 캡션 | 검색 노출용 키워드 포함. 첫 줄에 후킹 반복 |
| 주제 | **일관된 주제**를 유지해야 계정 단위로 배포가 붙는다 |
| 한글 조판 | `word-break: keep-all` 필수. 없으면 '맞춰/주는'처럼 한 단어가 갈려 첫 3초에 읽히지 않는다 |

### 1-4. 자동화 시 지켜야 할 선

- ✅ **Meta 공식 Graph API 게시만 사용.** 하루 100건 제한(캐러셀은 몇 장이든 1건으로 계산) — 우리 규모에서는 사실상 무제한.
- ❌ **비공식 자동화 금지**: 좋아요 봇, 팔로우 봇, 셀레늄 로그인 스크래핑, DM 자동 발송. 전부 ToS 위반이고 계정 정지 사유다. 이 설계에는 넣지 않는다.
- 🔒 **발행은 사람이**: 스크립트가 초안까지 만들고, 실제 `media_publish` 호출은 사용자가 승인한 뒤에만 실행한다.

## 2. 시스템 아키텍처

```
scripts/ig/
  collect.mjs        ① RSS 수집        → data/ig/raw/YYYY-MM-DD.json
  dedupe.mjs         ② 중복 판정·클러스터링 → data/ig/issues/YYYY-MM-DD.json
  classify.mjs       ③ 규칙 기반 분류·스코어링
  brief.mjs          ④ 아침 브리핑 생성 → data/ig/briefs/YYYY-MM-DD.md
  render.mjs         ⑤ 캐러셀 HTML → PNG (Chrome headless, 의존성 0)
  publish.mjs        ⑥ 호스팅 업로드 + IG Graph API (승인 게이트)
  lib/
    feeds.json          RSS 소스 목록
    fingerprint.mjs     제목 정규화 · 지문 · 유사도
    taxonomy.json       카테고리 · 키워드 사전
    templates/          캐러셀 HTML 템플릿 (4:5 = 1080×1350)

data/ig/
  seen.json          최근 14일 누적 지문 인덱스 (과거 중복 판정용)
  raw/               수집 원본
  issues/            중복 판정·분류 완료본
  briefs/            사람이 읽는 아침 브리핑
  cards/YYYY-MM-DD/  생성된 캐러셀 PNG
```

### 왜 이렇게 나눴나

- **의존성 0**: RSS 파싱은 내장 `fetch` + 경량 XML 파서 자작, 이미지 렌더링은 이미 설치된 Chrome의 `--headless --screenshot`. npm 패키지를 늘리지 않는다. (기존 `docs/launch/gallery-src/*.html → gallery/*.png` 방식과 동일한 패턴 재사용)
- **각 단계가 파일로 결과를 남긴다**: 중간 단계만 다시 돌릴 수 있고, Claude Code가 아무 단계 결과나 읽어서 판단에 쓸 수 있다.
- **LLM은 필요한 곳에만**: 수집·중복판정은 결정론적 코드가 훨씬 빠르고 싸고 정확하다. Claude Code는 "오늘 이 8개 중 뭘 만들지"와 카피라이팅에만 쓴다.

## 3. ① 수집 — RSS

- Node 24+ 내장 `fetch`로 병렬 수집, 소스별 5초 타임아웃, 실패는 건너뛰고 로그만.
- RSS 2.0 / Atom 양쪽 파싱 (`<item>`과 `<entry>` 모두).
- 추출 필드: `title`, `link`, `pubDate`, `source`, `summary`(있으면).
- **수집 창**: 최근 24시간 + 어제 브리핑 이후 신규분. `pubDate` 없는 항목은 최초 발견 시각으로 대체.
- 소스는 `feeds.json`에서 관리 — 주제 니치가 정해지면 채운다. 구글 뉴스 RSS(`news.google.com/rss/search?q=키워드&hl=ko&gl=KR`)를 쓰면 키워드 하나당 피드 하나를 즉석에서 만들 수 있어 초기 커버리지 확보에 유리하다.

## 4. ② 중복 판정 — 요구사항의 핵심

**중복을 지우지 않고 "표시"한다.** 같은 이슈를 여러 매체가 다뤘다는 사실 자체가 "이건 진짜 이슈다"라는 신호이기 때문이다.

4단계로 판정한다 (구현 완료, 실측 튜닝 반영):

| 단계 | 방법 | 판정 |
|---|---|---|
| **1. URL 동일** | `utm_*`·`fbclid` 등 추적 파라미터 제거, 호스트+경로 정규화 | 완전 중복 |
| **2. 제목 유사도** | 조사 제거 어절 자카드(60%) + 글자 bigram 자카드(40%) | **≥ 0.55**면 같은 이슈 |
| **3. 고유명사 병합** | 유사도 0.20~0.55 구간에서, 공유 토큰 중 **IDF ≥ 2.5**인 것들의 합이 **≥ 2.8** | 같은 이슈로 추가 병합 |
| **4. 과거 대비** | `seen.json`의 최근 14일 지문과 대조 | `🔁 3일 전에 이미 다룸` 태그 |

**3단계가 필요한 이유**: 같은 사건도 매체마다 표현이 완전히 달라 유사도가 0.25까지 떨어진다.
실제로 "AI 성장사다리" 출범 기사 25건이 8개 클러스터로 흩어졌다. 사업명·기관명 같은 고유명사는
표현이 달라도 살아남으므로, 그걸 근거로 병합한다.

**여기서 얻은 교훈 두 가지** (둘 다 실제로 사고를 냈다):
1. IDF 합을 그냥 쓰면 안 된다. "소상공인+지원+모집"(합 5.5)처럼 흔한 단어 조합이 임계값을 넘고,
   Union-Find 특성상 연쇄로 이어져 무신사·한진·강진군 기사 **39건이 한 덩어리**가 됐다.
   → 고유명사급(IDF ≥ 2.5) 토큰만 합산하도록 바꿨다.
2. IDF는 "고유명사"와 "그날 우연히 드문 일반명사"를 구별하지 못한다. '진출·글로벌·최대·참여자·모집'이
   고유명사로 취급돼 또 오병합을 냈다. → 뉴스 상투어를 불용어로 대폭 확장했다(`lib/fingerprint.mjs`).
   여기에 2차 병합 결과 크기 상한(30건)을 안전장치로 뒀다.

실측(2026-08-03, 328건): 이슈 174개, 중복 묶임 31개, 최대 클러스터 25건(AI 성장사다리, 22개 매체).

브리핑 출력 예시:

```
🔥 [AI] 오픈AI 신규 모델 발표          ← 대표 기사
     └ 중복 4건 (테크크런치·연합·ZDNet·전자신문)   ← 4개 매체가 다룸 = 큰 이슈
🆕 [정책] 개인정보위 새 가이드라인 공개
🔁 [AI] 클로드 신기능                  ← 2일 전 브리핑에 이미 나옴
```

임계값 0.55는 시작값이다. 1주일 돌려보고 놓친 중복/과한 병합을 보며 조정한다.

## 5. ③ 분류 & 스코어링

**분류**는 `taxonomy.json`의 카테고리별 키워드 사전으로 1차 매칭한다. 매칭 신뢰도가 낮은 항목만 `needs_review: true`로 표시해 Claude Code가 아침에 판단한다. (전건을 LLM에 보내지 않는다 — 느리고 비싸고, 90%는 키워드로 충분하다.)

**스코어링**은 2026 알고리즘 신호를 그대로 역산한 4축이다:

| 축 | 의미 | 가중치 |
|---|---|---|
| `save` | 실용성 — 저장해두고 다시 볼 만한가 (방법·목록·기준·비교) | ×3 |
| `send` | 공유 유발 — 남에게 보낼 이유가 있나 (경고·마감·손해) | ×3 |
| `fresh` | 신선도 — 6h 이내 만점, 24h 지나면 감점 | ×2 |
| `spread` | 소스 다양성 — 클러스터 크기 (여러 매체 = 진짜 이슈) | ×2 |

상위 3건을 "오늘의 콘텐츠 후보"로 올린다.

## 6. ④ 아침 브리핑

`data/ig/briefs/YYYY-MM-DD.md` 한 장. 구성:

1. **오늘의 콘텐츠 후보 TOP 3** — 스코어·추천 후킹 문구·슬라이드 뼈대 제안
2. **카테고리별 신규 이슈** — 중복 배지·재등장 태그 포함
3. **어제 대비 변화** — 새로 뜬 주제, 사라진 주제
4. **판단 필요** — `needs_review` 항목 (Claude Code가 여기만 읽고 처리)

## 7. ⑤ 릴스 렌더링 (`render-reel.mjs`)

같은 슬라이드 JSON에서 **릴스 mp4**와 **캐러셀 PNG** 둘 다 뽑을 수 있다. 주력은 릴스다.

**파이프라인**: 슬라이드 JSON → HTML → Chrome headless 스크린샷(1080×1920) → ffmpeg 합성 → mp4 + 커버 JPG

**설계 결정 세 가지** (모두 실측으로 정해졌다):

1. **켄번스는 zoompan이 아니라 crop 팬으로.**
   zoompan은 9장 27초 영상에 **4분 28초**가 걸렸다(프레임마다 재스케일). 이미지를 8% 크게 잡고
   crop 창을 움직이는 방식으로 바꾸니 **90배 빨라졌다**. 화면이 움직인다는 목적은 동일하다.
   팬 방향은 4가지를 순환시켜 리듬을 준다.

2. **전환은 slideup.** 크로스페이드는 두 슬라이드의 텍스트가 겹쳐 아무것도 읽히지 않는 구간을 만든다.
   정보성 릴스는 가독성이 전부라 밀어내는 전환이 맞다.

3. **인코더는 h264_videotoolbox 우선**(없으면 libx264 폴백). 텍스트 위주라 비트레이트를 10M으로 넉넉히 준다 —
   낮으면 글자 가장자리가 뭉갠다. `yuv420p`는 인스타 호환 필수.

**안전 영역**: 릴스는 인스타 UI가 화면을 덮는다. 하단 ~340px(캡션·오디오·프로필), 우측 ~200px(버튼).
템플릿의 `padding: 200px 96px 420px`이 이걸 피한 값이다. 여기를 줄이면 자막이 버튼에 가린다.

**오디오**: 지금은 무음 트랙(anullsrc)을 넣는다. 오디오 트랙이 아예 없으면 일부 업로드 경로에서 처리에 실패한다.
`--audio <mp3>`로 배경음을 넣을 수 있지만, **저작권 있는 음원은 쓰지 말 것**. 인스타 내장 트렌딩 오디오는
앱에서만 붙일 수 있고 Graph API 게시본에는 넣을 수 없다 — 자동 게시와 트렌딩 오디오는 양자택일이다.

## 8. ⑥ 게시 — 단계적으로

Instagram Graph API 게시에는 사전 준비가 필요하고, 특히 **Meta 앱 심사(`instagram_business_content_publish` 권한)는 승인까지 시간이 걸린다.** 그래서 게시를 마지막 Phase로 미루고, 그 전까지도 시스템이 매일 가치를 내도록 설계했다.

### 8-1. 준비 체크리스트

- [x] 인스타그램 **프로페셔널 계정**(비즈니스/크리에이터)으로 전환 — 완료
- [x] 페이스북 **페이지** 생성 및 인스타 계정과 연결 — 완료
- [ ] Meta 개발자 앱 생성 (앱 유형: **비즈니스**)
- [ ] 앱에 **Instagram** 제품 추가 → 인스타 계정 연결
- [ ] 권한 요청: `instagram_business_basic`, `instagram_business_content_publish`
- [ ] **앱 검수(App Review) 제출** — 권한별로 용도 설명과 **동작 스크린캐스트**를 요구한다. 여기가 시간이 가장 오래 걸린다
- [ ] 승인 후 토큰 발급 (아래 8-2)
- [ ] `IG_USER_ID` 확인 — `GET /me/accounts` → 페이지의 `instagram_business_account.id`

### 8-2. 토큰 — 갱신이 필요 없게 발급할 것

토큰 종류를 헷갈리면 60일마다 자동화가 멈춘다.

```
단기 사용자 토큰 (1시간)
  → 장기 사용자 토큰 (60일)
    → 페이지 액세스 토큰  ← 이걸 쓴다
```

**장기 사용자 토큰에서 파생한 페이지 액세스 토큰은 만료되지 않는다.** 사용자 토큰을 그대로 쓰면
60일마다 갱신해야 하므로, 반드시 페이지 토큰까지 내려가서 발급받을 것.

발급한 토큰은 `.env.local`(이미 gitignore 대상)에 두고 셸에 export 해서 쓴다. **커밋 금지.**

```bash
export IG_USER_ID=...
export IG_ACCESS_TOKEN=...
```

### 8-3. 게시 흐름 (구현 완료)

```bash
# 1) mp4 를 공개 URL 로 (Graph API 는 로컬 파일을 받지 않는다)
node scripts/ig/upload.mjs --slug <슬러그> --deploy

# 2) 컨테이너 생성 + 처리 완료까지 — 여기서 멈춘다
node scripts/ig/publish.mjs --slug <슬러그>

# 3) 미리보기 확인 후 발행
node scripts/ig/publish.mjs --slug <슬러그> --confirm
```

내부적으로:
1. mp4 → Firebase Hosting `/ig/<날짜>/<슬러그>.mp4` (firebase.json 에 CORS·캐시 헤더 추가함)
2. `POST /{ig-user-id}/media` — `media_type=REELS`, `video_url`, `cover_url`, `caption`
3. `GET /{container-id}?fields=status_code` 를 **FINISHED 될 때까지 폴링** — 영상은 즉시 준비되지 않는다
4. **여기서 정지.** 영상 URL·캡션을 출력하고 멈춘다
5. `--confirm` 을 붙였을 때만 `POST /{ig-user-id}/media_publish`

토큰 없이 요청 형태만 보려면 `--dry-run` 을 쓴다.

**주의할 점**
- ⚠️ **5~90초 + 9:16이 아니면 릴스 탭에 노출되지 않고 일반 동영상으로 게시된다.** `render-reel.mjs` 가 범위를 벗어나면 경고한다.
- 컨테이너는 **24시간 뒤 만료**된다. 그 안에 발행하지 않으면 다시 만들어야 한다.
- `firebase deploy` 는 `out/` 전체를 배포한다. `next build` 가 최신인지 확인하고 돌릴 것.
- 게시 한도는 24시간 이동창 기준 100건. `publish.mjs` 가 매번 남은 한도를 확인한다.

`GET /{ig-id}/content_publishing_limit`으로 잔여 한도를 매번 확인하고 로그에 남긴다.

## 9. 실행 Phase

| Phase | 산출물 | 상태 | 외부 의존 |
|---|---|---|---|
| **1** | 수집 + 중복 판정 + 분류 + 아침 브리핑 | ✅ **완료** (328건 → 이슈 174개 검증) | 없음 |
| **2** | 스케줄링 (매일 아침 자동 실행) | ⬜ 남음 (30분) | 없음 |
| **3** | **릴스 mp4 자동 생성** + 캐러셀 PNG | ✅ **완료** (27.2초 릴스 검증) | 없음 (Chrome + ffmpeg) |
| **4** | Hosting 업로드 + 미리보기 | ✅ **완료** (`upload.mjs`) | Firebase (이미 사용 중) |
| **5** | Graph API 릴스 게시 (승인 게이트) | ✅ **코드 완료** (`publish.mjs`) | **Meta 앱 심사 — 남은 유일한 병목** |

코드는 전부 끝났다. 남은 건 **Meta 앱 심사 승인 하나**다(8-1 체크리스트).
승인 전까지도 매일 아침 브리핑과 릴스 초안은 쌓이므로, 심사를 신청해두고 콘텐츠를 먼저 만들면 된다.
심사가 통과되면 `IG_USER_ID`·`IG_ACCESS_TOKEN`만 넣고 `publish.mjs` 를 돌리면 게시가 시작된다.

## 10. 스케줄링

**Claude Code 스케줄 태스크**를 쓴다. 이유: 매일 아침 스크립트만 도는 게 아니라, **결과를 읽고 판단하는 단계가 필요하기 때문**이다.

```
매일 07:00
  → Claude Code 기상
  → collect → dedupe → classify → brief 실행 (결정론적)
  → 브리핑을 직접 읽음
  → needs_review 항목 분류 확정
  → TOP 3 중 오늘 만들 1건 선택 + 슬라이드 카피 작성
  → render 실행 → PNG 완성
  → 사용자에게 "오늘 브리핑 + 캐러셀 초안" 보고
```

순수 cron(GitHub Actions·launchd)은 판단 단계를 못 한다. 반대로 전부 LLM에 맡기면 느리고 비싸다. 이 분담이 정확하다.

## 11. 사용법

하루 전체 흐름:

```bash
# ① 아침 파이프라인 (수집 → 중복판정 → 분류 → 브리핑)  ※ 매일 07:00 자동 실행됨
node scripts/ig/morning.mjs

# ② 릴스 렌더링 — 주력. mp4 + 커버 JPG
node scripts/ig/render-reel.mjs --slug <슬러그>

# ③ 공개 URL 로 업로드
node scripts/ig/upload.mjs --slug <슬러그> --deploy

# ④ 컨테이너 생성 후 정지 → 확인 → 발행
node scripts/ig/publish.mjs --slug <슬러그>
node scripts/ig/publish.mjs --slug <슬러그> --confirm
```

캐러셀도 필요하면 같은 draft 로 뽑는다: `node scripts/ig/render.mjs --slug <슬러그>`

슬라이드별 노출 시간은 draft JSON의 `sec` 필드로 조절한다(생략하면 유형별 기본값: hook 3.5 / point 3.0 / summary 4.5 / cta 4.0초).

단계별로 따로 돌리려면 `collect.mjs` → `dedupe.mjs` → `classify.mjs` → `brief.mjs` 순으로 실행한다.
각 단계가 파일로 결과를 남기므로 중간부터 다시 돌릴 수 있다.

**튜닝 포인트**
- `lib/feeds.json` — RSS 소스. 구글 뉴스는 `window`(when: 연산자)를 꼭 붙일 것. 없으면 관련성 순 정렬 탓에 몇 달 전 기사가 섞인다.
- `lib/taxonomy.json` — 카테고리 키워드, 니치 게이트, 저장/공유 신호어, 카테고리별 저장 잠재력.
- `lib/fingerprint.mjs` STOPWORDS — 오병합이 보이면 원인이 된 상투어를 여기에 추가한다.

## 12. 남은 작업

1. **Meta 앱 심사 신청** — 8-1 체크리스트. 코드는 다 됐고 이것만 남았다.
2. **니치 사전 보강** — 1~2주 운영하며 미분류·오병합 사례를 모아 `taxonomy.json`과 STOPWORDS를 채운다.
3. **성과 회수 루프** — 게시가 시작되면 `GET /{media-id}/insights`로 조회수·저장·공유를 받아와
   어떤 후킹·주제가 실제로 퍼졌는지 스코어링에 되먹인다. 지금 스코어는 사전 추정치일 뿐이다.
4. **글로벌 확장(선택)** — 릴스는 국경을 넘지만 인스타는 언어·관심사로 시청자를 매칭한다.
   한국 지원금 정보는 구조적으로 한국 시청자가 상한이다. 진짜 글로벌을 노리면 언어 의존도가 낮은
   니치(예: AI 도구 활용)로 `feeds.json`·`taxonomy.json`을 갈아끼우고 영어 자막을 넣어야 한다.
   파이프라인 자체는 그대로 쓸 수 있다.
